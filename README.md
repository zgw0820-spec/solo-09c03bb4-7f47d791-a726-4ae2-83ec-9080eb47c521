# 边缘网关值班切换 Demo

FastAPI + SQLite 实现的边缘网关与操作网页。值班员切换处理较久的 HTTP 服务上游时，
已接纳的请求仍从原上游取回完整响应；新请求在确认切换后立即走新目标。

## 组成

| 组件 | 说明 |
| --- | --- |
| `gateway/` | FastAPI 网关：转发请求、操作 API、值班台网页（`/`）、SQLite 持久化 |
| `upstream/` | 演示上游：可设默认响应延迟（`DEFAULT_DELAY_MS`），请求参数 `delay_ms` 可覆盖；`/health` 供切换前探测 |
| `docker-compose.yml` | 一键启动**两个网关**（共用同一 SQLite 卷）+ 三个本地上游（alpha、beta、beta-alt） |
| `scripts/` | 本地（无 Docker）端到端验证脚本 |

## 运行

Docker Compose：

```bash
docker compose up --build
# 值班台网页: http://localhost:8080/  （gateway-a）
#             http://localhost:8081/  （gateway-b，与 A 共用 SQLite）
```

演练“改地址”：把 `beta` 目标的地址换到另一个上游后重启网关：

```bash
BETA_URL=http://upstream-beta-alt:8000 docker compose up --build
```

两个网关必须使用 **不同且稳定** 的 `GATEWAY_ID`（compose 已配好 `gateway-a` /
`gateway-b`；未设置时默认取主机名）。同一主机上并行运行多个共用 SQLite 的网关时，
默认主机名会重合，必须显式设置不同 ID——否则一个网关启动时会把对端当作“自己的上一次
实例”，误清对端的在途记录并覆盖其登记快照。

本地直接跑（无需 Docker）：

```bash
./scripts/run_local.sh        # 原有切换语义 + kill -9 重启恢复，共 32 项断言
./scripts/run_binding.sh      # 地址变更/改回、有效期、双网关共用 SQLite 交错，共 48 项断言
```

## 语义与实现要点

- **已接纳请求走原上游**：`/api/call` 在接纳时原子地快照当前路由**及生效地址**
  （`db.admit` 把 `url` 一起写入 `inflight`），随后无论路由如何切换、上游登记地址
  如何变化，都从快照地址取回完整响应。
- **生效地址固定，不暗中跟随登记**：路由表同时保存确认切换时的地址与登记修订
  （`routes.current_url/current_revision`）。只改 `UPSTREAMS` 里的地址**不会**
  把在流流量或新流量引向未经探测的新地址；网页会提示“登记地址与生效地址不一致”，
  当前目标出现在候选列表里标为“待确认”，探测新地址成功后再确认才会采用它。
- **先探测后确认**：`POST /api/switch/probe` 只探测候选（`/health` + `/work`），
  从不改写路由——探测期间请求继续走旧目标，探测失败维持原路由；
  `POST /api/switch/commit` 才把路由切到新目标。
- **探测与登记身份绑定**：每条探测记录都绑定它实际探测的 **地址 URL**、
  **该地址的登记修订号 `revision`**（`upstreams.revision`）以及探测时的
  **路由版号**。确认时三者都必须和当前状态一致，否则拒绝：
  - 地址每次变化（含改回旧地址）都会使 `revision` 自增，此前所有探测立即失效，
    **改回旧地址也不能复用**；网页上该探测显示“失效（地址已变化）”。
  - 数据库升级前产生的旧探测没有地址绑定，一律不可用于确认。
  - 探测有有效期（`PROBE_TTL_SECONDS`，默认 60s），过期后需重新探测。
- **重启语义**：地址未变且探测仍在有效期内的重启 **保留** 探测（登记是幂等的，
  `revision` 不变）；只有地址真的变化才使探测失效。
- **可下线提示**：非当前目标的在途数清零时，状态接口给出 `can_offline: true`，
  网页对应行显示“可下线 ✓”。
- **版号防交错**：网页每次操作都携带它所见的路由版号；确认切换按
  `version = base_version` 做比较并交换（CAS）。两次切换交错时，先到的确认生效，
  迟到的确认（含迟到探测发起的确认）收到 `409 version_conflict`，不得覆盖已生效路由；
  此时目标、版号与地址均保持原样。
- **多网关共用 SQLite**：所有“读-判断-写”（登记、接纳快照、确认）都在
  `BEGIN IMMEDIATE` 事务内完成，多个网关进程间串行化：
  - 并发确认同一版号只会有一个成功，另一个收到 409，版号只加一次；
  - 一个网关改登记后，另一个网关基于旧地址的探测立即不能再确认；
  - 启动清理只清自己上一次实例留下的在途记录，不会误清对端网关的在途。
  - 每个网关只在与**自己**上次登记不同的名字上应用配置，因此对端重启不会
    悄悄把本网关刚改过的地址回退，也不会为未改动的地址制造 `revision` 漂移。
- **重启恢复**：路由与上游登记在 SQLite 中持久化，重启后按已登记路由接流量。

## 操作 API

| 方法/路径 | 说明 |
| --- | --- |
| `GET /api/state` | 当前路由（目标+地址+版号）、各上游登记修订/在途数、在途明细、最近探测及其有效性 |
| `POST /api/call` | 发起转发请求 `{delay_ms?, path?}`，返回服务目标、实际地址与上游响应 |
| `POST /api/switch/probe` | 探测候选 `{target, base_version}`，不改路由；返回 `committable` 及地址/版号匹配情况 |
| `POST /api/switch/commit` | 确认切换 `{target, base_version, probe_id}`；失败时 `error` + `reason`，路由与版号不变 |

确认失败的状态码：`409 version_conflict`（路由已变更，含对端先提交）、
`400 probe_invalid`（探测失败/地址已变化/版号不匹配）、`400 probe_stale`（探测过期）、
`404 unknown_target`。网页据此提示“请重新探测”。确认成功时 `same_target: true`
表示这是把当前目标切换到其新登记地址（同样必须先探测）。

## 验证

`scripts/run_local.sh` 启动两个上游与网关，执行 `scripts/smoke_test.py`
两阶段共 32 项断言：切换语义、探测失败维持路由、交错切换版号冲突、
慢请求从原上游取回完整响应、在途清零才可下线、`kill -9` 后重启的在途清理与路由保持。

`scripts/run_binding.sh` 另起三个上游 + 两个共用 SQLite 的网关，通过真实 HTTP
验证 48 项断言：同地址重启保留有效期内的探测、地址变更后旧探测失效、改回旧地址
仍不复用、过期探测不可用、`UPSTREAMS` 改地址后生效地址不暗中跟随且须重新探测确认、
跨网关登记变更使探测失效、双网关并发确认恰好一个成功、迟到的跨网关确认保留原目标
与版号、在途请求在登记被改后仍从接纳地址取回完整响应。

另有两个直接调用 `db` 层的补充检查（迁移与“探测进行中登记变化”竞态）：
旧库升级后旧探测不可用；同地址重启探测仍可用；探测读到的登记在确认前变化则确认被拒。
